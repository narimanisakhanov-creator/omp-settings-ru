# участие

граница проекта — отображаемые метаданные `/settings`, не значения, обработчики или пользовательские файлы.
используй [глоссарий](docs/glossary.md), [архитектуру](docs/architecture.md) и [нормы поведения](CODE_OF_CONDUCT.md).
сложное сопровождение — распространение, обновление источников, автоматизация и выпуск — вынесено в [docs/maintenance.md](docs/maintenance.md).

## граница публичного репозитория

`main` содержит только потребительские материалы плагина: runtime и переводы `src/`, снимки метаданных хоста в `test/fixtures/host-snapshots/`, тесты, документацию, CI и release tooling.

личная работа агента и сопровождающего остаётся вне checkout: specs и планы (`.kiro/`), agent-инструкции и skills (`.agents/`), трассы сессий и заметки (`.hiro/`, `.triage/`, `.orca/`), промпты, логи сессий, отчёты о работе, материалы ревью, приватные backups канала и scratch-каталоги вроде `.tools/` и `.smoke/`. локальные снимки `baseline/` — тоже вне Git: канонический экземпляр один, `test/fixtures/host-snapshots/`. `.gitignore` закрывает известные каталоги от случайного `git add -A`; `git check-ignore -v <путь>` показывает сработавшее правило. ignore не заменяет решение: такие файлы не добавляй и через `git add -f`, а отчёты и планы храни вне репозитория.

перед коммитом `git status` без `--ignored` должен показывать только файлы, нужные потребителю плагина.

`main` — единственная публичная ветка. ни один workflow не создаёт веток и не открывает PR: проверка upstream-кандидата кладёт результат в артефакт прогона, Dependabot держит `open-pull-requests-limit: 0`, а канал выпуска продвигается workflow-ом, а не веткой каталога. изменения вноси на `main` и сопровождай тегом выпуска.

## окружение

версии Bun, TypeScript и пакетов разработки определены `package.json` и `bun.lock`.

```text
bun install --frozen-lockfile --ignore-scripts
```

runtime получает живой реестр запущенного OMP; локальные пакеты нужны для сопровождения.
не загружай установленную и локальную копии плагина одновременно.

## перевод и записи ревью

- каталог — `src/translations/`; ключ настройки — технический путь, ключ варианта — исходный `value`.
- переводи названия, описания, предупреждения и статические подписи. сохраняй числа, команды, пути и технические имена; не добавляй обещаний к upstream-тексту.
- сохраняй старый вариант для старого источника; новый `sourceHash` и перевод добавляй после собственной проверки смысла, не массовой перезаписью хешей.
- provenance варианта должен перечислять реально наблюдавшиеся версии и платформы, а не предполагаемые.
- изменения источника отражай в `src/translations/variant-review.json`; independent reviewer в pipeline отключён (`semanticReview: "disabled"`), новые варианты не получают verdict и comparison, а `unreviewed-*` для них не считается провалом; исторические `independently-confirmed` записи сохраняются. `bun run release:check` проверяет схему, точные hashes и исторические identity, но не смысл нового перевода: semantic-ошибка может уйти в выпуск.
- динамические описания согласуй с `src/source-templates.ts`, `descriptionSource` и русским текстом с теми же `{placeholder}`; клавиши предоставляет хост.
- удаляя запись, проверь остальные версии матрицы. старый перевод под новым хешем получает новый вариант, а не перезапись старого.

исправление механизма сопровождай доменной регрессией на границы, переходы, владение дескрипторами или восстановление.
не добавляй проверки копий текста и mock-эхо. слои проекта — доменные проверки и e2e/smoke.

## матрица и peer-диапазон

`test/fixtures/host-snapshots/supported-hosts.json` связывает версии, алиасы пакетов и платформы, а `sha256` каждой записи указывает на снимок `<версия>-<платформа>.json` в том же каталоге. это единственный отслеживаемый экземпляр данных хоста: `baseline/` в checkout — локальный рабочий каталог для ручного экспорта, он игнорируется Git, и пути к снимкам берутся только из `scripts/maintenance/paths.ts`.
три уровня доказательств не заменяют друг друга:

- source-derived и native-package-registry фиксируют метаданные реестра, не панель;
- `installedEvidence` и `unavailableInstalledRuns` в существующем manifest — исторически зафиксированные локальные прогоны и пробелы, а не полный список текущих CI-прогонов;
- per-commit native CI receipts относятся к точному SHA, пакету и бинарнику, доступны в artifacts конкретного workflow и не переопределяют старые локальные записи.

обновляй запись вместе с исходниками и каталогом, сохраняя точное происхождение доказательств.

peer-диапазон — контракт потребителя, dev-пины — среда проверки; изменение одного не доказывает другое.
не объявляй широкий диапазон по похожести крайних версий.
структурный fallback по пути/хешу/платформе не обещает работу установленной панели на неизвестном хосте.

## проверки пакетов

```text
bun run check
bun run matrix:check
bun run release:check
```

`check` запускает TypeScript, доменные тесты, покрытие, drift, smoke расширения, smoke компонента панели и release hygiene.
`matrix:check` проверяет покрытие и drift по выбранной матрице; не подменяет installed smoke.
`release:check` проверяет pack allowlist, поиск паттернов секретов и схему записей `variant-review.json`, включая сохранность исторических identity.
сохраняй версии, платформу, SHA, вывод и код возврата; конфигурация CI не равна завершённому run.

## проверка установленного хоста

проверяй каждую заявляемую пару версия/платформа в одноразовом профиле без ключей, личных сессий и реальных назначений моделей.
для локального запуска checkout используй очищенное окружение и отдельный профиль:

```text
omp --profile omp-settings-ru-proof --no-extensions -e ./src/index.ts
```

автоматизированный native smoke запускается через `bun run smoke:installed --exercise`;
его CLI требует настоящий установленный executable и создаёт собственный изолированный профиль.

1. сохрани очищенные `omp --version`, `omp plugin list --json`, версию manifest, хеш загруженных файлов и executable.
2. проверь старт, русский `/settings`, описания, предупреждения, статические варианты и поиск `символов`.
3. измени безвредный bool/enum и верни назад; проверь техническое значение и смысл обработчика.
4. закрой панель, проверь `en`, `ru` и выбор без аргументов с повторным открытием.
5. проверь новую сессию с плагином, установку/удаление менеджером и новую сессию без него.
6. отдельно проверь отказ на некорректном реестре, сохранность сторонних изменений и восстановление после сбоя.

разделяй package registry, installed-host smoke и ревью кода.
для публичного снимка нужен читаемый PNG настоящей панели; лог и перенабранный SVG его не заменяют.
снимок относится к хешу загруженных при захвате файлов: поздний smoke других байтов не меняет его provenance.

## переход на marketplace

штатная установка — только marketplace; legacy npm-managed GitHub-установка больше не поддерживается и не документируется как способ установки. State-preserving переход из **одной** legacy npm user-установки выполняется одноразово из checkout:

```text
bun scripts/switch-channel.ts --home <isolated-home> --profile <named-profile> --executable <omp> --to marketplace --spec omp-settings-ru@omp-settings-ru --backup <new-private-backup.json> --apply
```

Закрой старые сессии и убери explicit `-e`/`--plugin-dir`/configured extension roots: они не являются установками и не видны в `plugin list`. `omp plugin list --json` должен показывать ровно одну legacy npm user-установку в каталоге профиля; project-scoped marketplace-копия или npm-запись вне этого каталога, а также уже выбранный marketplace отклоняются. Marketplace должен быть добавлен заранее; старый каталог из ветки переводится через `marketplace remove`, `add` нового URL и `marketplace update`, а не через `uninstall`.

Скрипт требует explicit named profile и `--apply`, а `--to npm` отклоняет до любых действий. До удаления он типизированно проверяет lock и сохраняет own state/settings с JSON types, `null`/`[]` features и disabled-state; чужие записи и неизвестные поля переносятся без изменений. Backup приватный, не перезаписывается. При сбое install частично поставленный marketplace сначала удаляется, затем восстанавливается точный старый npm-тег и own запись; если и это невозможно, скрипт сообщает точный backup и не выдаёт сбой за успех — не копируй весь старый lockfile поверх текущего. Для личного профиля нужна отдельная разрешённая операция; local proof использует только disposable homes. Обратный переход на npm не поддерживается.
